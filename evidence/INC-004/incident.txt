INC-004 - Service Failure
Evidence: Incident
Environment: Linux / WSL2

=== Controlled Failure ===

A controlled service failure was generated by changing the Java
main class configured in the systemd service.

Healthy configuration:

ExecStart=/usr/bin/java -cp app SreLabApp

Controlled faulty configuration:

ExecStart=/usr/bin/java -cp app SreLabAppBroken

The class SreLabAppBroken does not exist in the application.


=== Service Restart ===

After modifying the service configuration, systemd was reloaded
and the service was restarted.

Commands:

sudo systemctl daemon-reload
sudo systemctl restart sre-lab-app.service


=== Service State ===

Command:

systemctl status sre-lab-app.service

Observed:

Service state:

activating (auto-restart)

Process result:

status=1/FAILURE

systemd repeatedly attempted to restart the application because
the service was configured with:

Restart=on-failure


=== Journal Investigation ===

Command:

journalctl -u sre-lab-app.service

Relevant Java errors observed:

Error: Could not find or load main class SreLabAppBroken

Caused by:

java.lang.ClassNotFoundException: SreLabAppBroken


=== Restart Behavior ===

During the investigation, systemd restart counters were observed
increasing through values such as:

56
57
58

The application repeatedly failed and systemd continued attempting
to restart it.


=== Evidence Correlation ===

The service failure occurred after the configured Java main class
was changed from:

SreLabApp

to:

SreLabAppBroken

The Java runtime reported that SreLabAppBroken could not be found.

The process exited with status 1, causing systemd to activate the
configured restart policy.


=== Diagnosis Supported by Evidence ===

The failure was caused by an invalid Java main class configured
in ExecStart.

The restart policy did not correct the configuration error.

Instead, systemd repeatedly restarted a process that could not
successfully initialize.
